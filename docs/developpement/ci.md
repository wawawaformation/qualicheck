# CI / CD


`.github/workflows/ci-dev.yml` — déclenché sur push sur toute branche sauf `main`/`staging` (couvre `dev`, la branche de travail principale, et toute branche annexe type `veille`). Étapes : `uv sync` → `ruff check` → `scripts/migration.py` (contre un service `pgvector/pgvector:pg17` éphémère, pour vérifier que les migrations s'appliquent) → `pytest tests/unit tests/integration`.

- **Secrets BDD** (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`) gérés via **GitHub Secrets**, pas via `.env` — le `.env` reste strictement local, jamais commité ; les secrets CI sont une configuration séparée côté GitHub. `POSTGRES_TEST_DB` du workflow réutilise volontairement la valeur du secret `POSTGRES_DB` (aucun secret dédié créé) — la base du service CI étant déjà éphémère à chaque run, cette réutilisation ne recrée pas le risque de l'incident du 2026-07-25.
- Le CI n'exécute **pas** `scripts/ingestion.py` (évite de vrais appels LLM facturés à chaque push) — les tests couvrent le code applicatif (unitaire + intégration), pas le pipeline d'ingestion réel.
- `tests/migration/` (et `tests/acceptance/`) sont volontairement exclus de ce workflow — scope de tests plus léger pour une branche de travail.
- `.github/workflows/cd-staging.yml` — déclenché sur push sur `staging` (survient au merge d'une PR `dev → staging`). Tourne sur un runner self-hosted enregistré sur le serveur personnel de David (cloclo) : migrations Alembic (`make migration`), déploiement (`make up`), puis rejeu de la suite d'acceptance existante (`make api-regles-acceptance`) comme garde-fou sur l'instance réellement déployée. Pas de rollback automatique en cas d'échec de l'acceptance — voir `docs/superpowers/specs/2026-07-28-cd-staging-design.md` pour la justification complète et le runbook des prérequis manuels (`docs/developpement/deploiement_staging.md`).
- **`main` n'a volontairement aucun workflow associé** (2026-08-29) : cette branche est réservée à la bascule vers l'hébergement de production réel sur Infomaniak (`conception/conception.md` § Choix techniques — LLM/embedding de prod). Tant que l'application est en construction, la livrer sur un environnement de production n'a pas de sens — `staging` (sur `cloclo`) sert d'environnement de démonstration réel en attendant. Le pipeline `main` sera ajouté au moment de la bascule Infomaniak, pas avant.
