- **2026-09-16** — Premier déploiement staging réel depuis longtemps (68 commits accumulés sur `dev` : mécanisme de refus complet, config LLM par domaine, scission BDD) — diagnostic complet d'une chaîne d'échecs en cascade avant d'y arriver :
  - Push direct de branche refusé (`non-fast-forward`) : `staging` avait 20 commits de merge propres à son historique, pas une vraie divergence de contenu — investigué avant d'envisager un `--force` (jamais utilisé sur `staging`).
  - PR ouverte (`tea pull create`) : merge API systématiquement refusé (`405 Method Not Allowed`, message générique). Éliminé méthodiquement, dans l'ordre : règles de protection de branche (inspectées puis entièrement neutralisées via l'API `branch_protections`), `mergeable: true` confirmé côté API, push direct confirmé bloqué par une règle distincte et fonctionnelle (`enable_push: false`, message clair celui-là) — la vraie cause restait ailleurs.
  - Cause trouvée dans l'UI Gitea, pas l'API : la PR exigeait une branche "synchronisée" avant d'accepter le merge, message que l'API masquait derrière une erreur générique. Résolu en cliquant "Actualiser la branche par fusion".
  - **Deuxième diagnostic, plus profond** : le merge obtenu (`200 OK`) ne rapatriait aucun contenu réel — vérifié directement sur le contenu de `staging` (fichiers attendus absents) plutôt que de faire confiance au statut HTTP. Cause racine : `gitea/dev` n'avait jamais été repoussé pendant toute la session (seul `origin`/GitHub avait reçu les commits) — resté bloqué sur un commit du 2026-09-10, six jours d'écart. La PR avait donc été construite sur une base obsolète dès sa création.
  - Corrigé par un `push --force` **ciblé sur `gitea dev` uniquement** (jamais sur `origin`, jamais sur `staging`) pour aligner la copie stale sur la vraie branche de référence — décision prise après avoir confirmé qu'aucun contenu réel n'était perdu (le commit écrasé n'était qu'un artefact de merge créé par inadvertance). Nouvelle PR ouverte, `head_commit_id` vérifié explicitement avant merge cette fois.
  - Déploiement final vérifié de bout en bout sur l'infrastructure réelle, pas seulement sur le statut du pipeline : `curl https://regles.qualicheck.koabana.fr/version` recoupé avec le SHA du commit de merge attendu, `/health` confirmant la base joignable.
  - Aucune étape de correction n'a été appliquée sans confirmation explicite préalable (force-push notamment) — actions à fort impact sur un environnement partagé toujours soumises avant exécution.
